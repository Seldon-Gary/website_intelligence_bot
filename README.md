# Competitor Radar

Telegram-бот, который следит за офферами конкурентов. По команде агент открывает сайт конкурента **в настоящем браузере**, сам обходит его, собирает предложение целиком — заголовок, выгоды, тарифы, кнопки, соцдоказательства — и присылает в чат сводку со скриншотом. Повторный запуск показывает, что изменилось с прошлого раза.

Браузером агент управляет через готовый MCP-сервер **[@playwright/mcp](https://github.com/microsoft/playwright-mcp)**.

---

## Зачем здесь MCP, а не обычный парсер

Это главный вопрос проекта, поэтому отвечу сразу.

Обычный парсер знает селекторы: «цена лежит в `.pricing__amount`». Он работает ровно на одном сайте и ломается, когда там меняют вёрстку. Под каждого нового конкурента его надо переписывать.

Playwright MCP даёт модели **живой браузер с состоянием между вызовами**. Модель открывает страницу, читает её содержимое, сама находит ссылку на тарифы, переходит, читает дальше — в одной браузерной сессии, с сохранёнными куками и историей. Решение «куда кликнуть» принимает она, глядя на страницу, а не мы заранее в коде.

Поэтому добавление нового конкурента здесь — это одна команда `/add`, а не работа программиста.

Своей функцией такое дёшево не повторить: каждый вызов был бы холодным стартом браузера, без общего состояния. Именно ради этого состояния и нужен протокол.

## Архитектура

```
Telegram ──► bot (aiogram)                 процесс 1: тонкий клиент
                 │
                 ▼  http://127.0.0.1:8000
            api (FastAPI + SQLite + воркер)    процесс 2
                 │
                 ├─► Claude (tool_runner)
                 │        │
                 │        └── MCP stdio ──► npx @playwright/mcp ──► Chromium
                 │
                 └─► Telegram Bot API   (шлёт готовый результат в чат)
```

Обход занимает 1–3 минуты — Telegram столько не ждёт. Поэтому бот кладёт задачу в очередь через `POST /scans` и сразу отвечает «принял», а результат уходит в чат из фонового воркера. API-слой здесь не для галочки: без него бота пришлось бы держать заблокированным на всё время обхода.

### Две фазы работы агента

| Фаза | Что делает | Файл |
|---|---|---|
| **1. Обход** | Агент водит браузер через MCP и пишет заметки о том, что увидел | `api/agent/crawl.py` |
| **2. Структурирование** | Отдельный вызов превращает заметки в строгую схему `Offer` | `api/agent/extract.py` |

Разделение сделано намеренно: если агент дошёл только до половины страниц, заметки всё равно есть и карточка соберётся из того, что успели увидеть. Одним заходом с жёсткой схемой мы бы теряли всё.

**Цены ловятся в двух видах.** Если у конкурента есть тарифные планы — они попадают в `plans` с названием и стоимостью. Если планов нет, а оплата поштучная или «по запросу», цена не теряется: она пишется текстом в `pricing_note`. Оба поля участвуют в сравнении замеров, так что подорожание видно в любом случае.

## Быстрый старт

Нужны **Python 3.10+** и **Node.js** (для `npx`).

```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
npx playwright install chromium

copy .env.example .env    # заполни BOT_TOKEN и ANTHROPIC_API_KEY
```

### Доступ к Claude

Проект ходит к Claude через **[ProxyAPI](https://proxyapi.ru)** — формат запросов там идентичен оригинальному, поэтому официальный SDK работает как есть, без адаптеров. Меняется только адрес:

```
ANTHROPIC_API_KEY=<ключ ProxyAPI>
ANTHROPIC_BASE_URL=https://api.proxyapi.ru/anthropic
```

Чтобы работать напрямую с `api.anthropic.com`, достаточно очистить `ANTHROPIC_BASE_URL` и положить в `ANTHROPIC_API_KEY` обычный ключ Anthropic. Больше ничего в коде менять не нужно.

Модель по умолчанию — **`claude-sonnet-5`**: для чтения лендинга её хватает, а стоит она заметно меньше Opus. Меняется в `.env` вместе с `EFFORT` (`low` … `max`), код трогать не надо.

Каждый скан считает израсходованные токены — они пишутся в лог, в карточку и в БД. Обход это цикл, где история пересылается на каждом ходу, поэтому цена видна только в сумме по всем запросам. Чтобы рядом с токенами показывалась и стоимость, укажи свои ставки (у ProxyAPI свой прайс):

```
PRICE_INPUT_PER_MTOK=0
PRICE_OUTPUT_PER_MTOK=0
```

Нули = показываем только токены.

Проверить, что доступ работает:

```powershell
.\venv\Scripts\python.exe -m scripts.check_claude
```

Скрипт проверяет три вещи, на которых держится проект: обычный запрос, **tool use** (фаза обхода) и **структурированный вывод** (сборка карточки). Если что-то из этого не проксируется — видно сразу, а не на первом скане.

Запуск в двух терминалах:

```powershell
.\run_api.ps1    # терминал 1 — API на 127.0.0.1:8000
.\run_bot.ps1    # терминал 2 — бот
```

Swagger: <http://127.0.0.1:8000/docs>

### Проверить MCP-сервер отдельно

```powershell
.\venv\Scripts\python.exe -m scripts.check_mcp https://example.com
```

Скрипт подключается к Playwright MCP, печатает список его инструментов, открывает страницу и снимает скриншот — всё без бота и без API. Показывает, что MCP-сервер это самостоятельная сущность.

## Прокси

Весь внешний трафик может идти через локальный прокси — задаётся одной переменной в `.env`:

```
PROXY_URL=socks5://127.0.0.1:1080
```

Пустое значение означает работу напрямую. Куда прокси подставляется:

| Что | Где в коде |
|---|---|
| Бот → Telegram | `AiohttpSession(proxy=...)` в `bot/main.py` |
| API → Telegram | `httpx.AsyncClient(proxy=...)` в `api/notify.py` |
| Браузер → сайты конкурентов | флаг `--proxy-server` в `api/agent/mcp_session.py` |
| API → ProxyAPI | **без прокси** — ProxyAPI сам решает вопрос доступа. Флаг `ANTHROPIC_VIA_PROXY` оставить `false` |
| Бот → API | **без прокси** — это `127.0.0.1`, гнать локальный трафик наружу незачем |

Проверить канал до Telegram:

```powershell
curl -x $env:PROXY_URL https://api.telegram.org/bot<ТОКЕН>/getMe
```

Если прокси окажется `socks5://`, нужные зависимости (`httpx[socks]`, `aiohttp-socks`) уже стоят.

## Границы доверия

Агент читает чужие сайты, а на чужом сайте может быть написано что угодно — в том числе текст, адресованный ему. Поэтому возможности агента ограничены по проекту, а не по инструкции в промпте:

- **У модели нет доступа к базе.** Она умеет только водить браузер. Все данные о конкурентах читает и пишет `api`. Никакая инструкция со стороннего сайта не заставит агента прочитать чужие данные — у него физически нет такого инструмента.
- **`owner_tg_id` берётся из апдейта Telegram**, а не из текста сообщения, и модели не передаётся вообще. Фильтр по владельцу живёт в одной функции `db.owned_competitor`, чтобы его нельзя было забыть в отдельном роуте.
- **Из 24 инструментов MCP-сервера агенту отданы 6** — навигация, чтение, поиск по странице, клик, ожидание. Заполнение форм, загрузка файлов и выполнение произвольного JS на странице ему недоступны.
- **Обход ограничен** четырьмя страницами и потолком ходов цикла.
- Секреты живут в `.env`, он в `.gitignore`.

## Структура

```
api/
  main.py          REST-роуты
  worker.py        очередь сканов
  db.py            SQLModel: Competitor, Scan, Snapshot
  schemas.py       схема Offer (её заполняет фаза 2)
  diff.py          сравнение двух замеров
  notify.py        отправка результата в Telegram
  render.py        форматирование для чата
  agent/
    mcp_session.py подключение к Playwright MCP
    crawl.py       фаза 1 — обход
    extract.py     фаза 2 — структурирование
    prompts.py
bot/
  main.py          команды aiogram
  api_client.py    HTTP-клиент к своему API
scripts/
  check_mcp.py     проверка MCP-сервера в отрыве от проекта
```
