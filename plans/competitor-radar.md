# Competitor Radar — Telegram-бот с Playwright MCP

## Контекст

Учебный проект Zerocoder. Требования сдачи: репозиторий на GitHub + скриншоты/видео работы **MCP-сервера, API и Telegram-бота**. Нужно подключить готовый MCP-сервер (не писать свой).

Берём `@playwright/mcp` — один из немногих серверов, где протокол реально незаменим: он держит живой браузер между вызовами, и модель сама решает, куда кликать, глядя на страницу, а не по захардкоженным селекторам.

**Что делает продукт.** Бот следит за лендингами конкурентов. По команде агент обходит сайт конкурента (главная → тарифы → продукт), собирает оффер целиком — заголовок, УТП, CTA, тарифы, соцдоказательства — складывает снапшот в БД и присылает в чат сводку со скриншотом. Повторный скан показывает, что изменилось с прошлого раза.

**Решения, зафиксированные с Гари:**
- Данные: оффер целиком (не только цены)
- Запуск обхода: только по команде из бота, без планировщика
- Запуск проекта: **локально, два процесса, без Docker**
- Список конкурентов: CRUD через бота
- Прокси: адрес читается из `.env`, значение Гари впишет сам

**Почему без Docker.** Docker Desktop на машине не установлен, его установка требует админ-прав, компонентов Windows и перезагрузки. В требованиях сдачи контейнеров нет — три артефакта (MCP-сервер, API, бот) прекрасно живут без них. Заодно исчезает целый класс проблем: прокси остаётся честным `127.0.0.1`, не надо тащить Chromium и Node в образ. Docker MCP из плана убран — управлять нечем.

## Архитектура

```
Telegram ──► bot (aiogram)          процесс 1: тонкий клиент, только HTTP
                 │
                 ▼  http://127.0.0.1:8000
            api (FastAPI + SQLite + воркер)     процесс 2
                 │
                 ├─► Claude Opus 5 (tool_runner)
                 │        │
                 │        └── MCP stdio ──► npx @playwright/mcp ──► Chromium
                 │
                 └─► Telegram Bot API   (шлёт готовый результат в чат)
```

**Два процесса.** `api` содержит веб-слой, фоновый воркер и поднимает Playwright MCP как подпроцесс. `bot` тонкий: разбирает команды, дёргает REST, рендерит ответы. Один общий venv на оба.

**Почему воркер вообще нужен.** Обход конкурента занимает 1–3 минуты, Telegram столько ждать не будет. Бот кладёт задачу через `POST /scans`, мгновенно отвечает «принял в работу», а `api` по завершении сам шлёт результат в чат через Bot API. Это честно оправдывает наличие API-слоя в проекте — он не декоративный.

**SQLite пишет только `api`** — один процесс на запись, никаких блокировок.

## Сеть: внешний трафик через локальный прокси

Telegram Bot API и браузер Playwright ходят наружу через локальный прокси. Всё запускается на одной машине, поэтому адрес — обычный `127.0.0.1`, без всяких `host.docker.internal`.

`.env`:

```
PROXY_URL=            # напр. socks5://127.0.0.1:1080 или http://127.0.0.1:8080
ANTHROPIC_VIA_PROXY=false
BOT_TOKEN=
ANTHROPIC_API_KEY=
API_BASE_URL=http://127.0.0.1:8000
```

**Пустой `PROXY_URL` = работаем напрямую.** Код читает переменную и, если она пустая, не настраивает прокси вообще. Это позволяет начать сборку до того, как Гари определится с адресом, и не ломает запуск.

### Где прописывается прокси

| Что | Как |
|---|---|
| **Бот → Telegram** (aiogram) | `AiohttpSession(proxy=PROXY_URL)`, сессия передаётся в `Bot(token, session=...)` |
| **`api` → Telegram** (`notify.py`) | `httpx.AsyncClient(proxy=PROXY_URL)` |
| **Playwright MCP → сайты конкурентов** | флаг `--proxy-server` в аргументах запуска stdio-сервера |
| **`api` → Anthropic** | опционально по флагу `ANTHROPIC_VIA_PROXY`: `Anthropic(http_client=DefaultHttpxClient(proxy=PROXY_URL))` |
| **`bot` → `api`** | **без прокси** — локальный `127.0.0.1:8000`, гонять через внешний прокси нельзя |

### Зависимости под оба протокола

Протокол прокси пока неизвестен, поэтому ставим поддержку обоих сразу — это дёшево:

- `httpx[socks]` — иначе httpx не умеет `socks5://`
- `aiohttp-socks` — то же для aiogram

Для `http://`-прокси обе библиотеки работают из коробки. Playwright `--proxy-server` принимает и `http://`, и `socks5://`.

### Проверка прокси до всякой логики

Когда Гари даст адрес — первым делом:

```
curl -x %PROXY_URL% https://api.telegram.org/bot<TOKEN>/getMe
```

Должен вернуться JSON с данными бота. Не работает — чиним здесь, а не после того как написан бот.

## Ключевое решение: обход и извлечение разнесены на две фазы

**Фаза 1 — агентный обход.** `tool_runner` с тулами Playwright MCP. Модель навигирует, читает снапшоты страниц, кликает по ссылкам на тарифы, делает скриншот главной. На выходе — накопленный текст того, что она увидела.

**Фаза 2 — структурирование.** Отдельный вызов `client.messages.parse()` с Pydantic-схемой поверх собранного материала. Даёт гарантированный формат.

Почему не одним заходом со `output_config.format`: смешивать длинный агентный цикл со строгой схемой хрупко — если агент упрётся в лимит или страница не откроется, ты теряешь всё. Разделив, получаешь материал даже при частичном обходе. Плюс на видео наглядно видно два разных этапа.

## Схема данных

**competitors** — `id`, `name`, `url`, `owner_tg_id`, `created_at`
**scans** — `id`, `competitor_id`, `status` (queued/running/done/error), `chat_id`, `started_at`, `finished_at`, `error`, `pages_visited`, `tool_calls_count`
**snapshots** — `id`, `competitor_id`, `scan_id`, `captured_at`, `offer_json`, `screenshot_path`

`tool_calls_count` пишем специально — на демо покажешь, сколько решений модель приняла сама.

**Схема оффера** (`schemas.py`):

```python
class Plan(BaseModel):
    name: str
    price: str | None
    period: str | None
    features: list[str]

class CTA(BaseModel):
    text: str
    placement: str          # hero / pricing / footer

class Offer(BaseModel):
    headline: str
    subheadline: str | None
    value_props: list[str]
    target_audience: str | None
    plans: list[Plan]
    ctas: list[CTA]
    social_proof: list[str]
    pages_visited: list[str]
```

## Эндпоинты API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/competitors` | добавить (url, name, owner_tg_id) |
| `GET` | `/competitors?owner_tg_id=` | список **своих** |
| `DELETE` | `/competitors/{id}` | удалить |
| `POST` | `/scans` | поставить обход в очередь → `{scan_id, status}` |
| `GET` | `/scans/{id}` | статус |
| `GET` | `/competitors/{id}/snapshot` | последний оффер |
| `GET` | `/competitors/{id}/diff` | что изменилось между двумя последними |
| `GET` | `/compare?owner_tg_id=` | сводная таблица по всем |

Swagger на `/docs` — это и есть демонстрация API-слоя для сдачи.

## Подключение Playwright MCP

```
pip install "anthropic[mcp]"       # Python 3.10+, у нас 3.12
npx playwright install chromium    # браузер один раз
```

MCP-коннектор в Messages API работает только по URL — stdio он не поднимет. Поэтому используем Python-хелперы: `stdio_client` → `ClientSession` → `async_mcp_tool(t, mcp_client)` → тулы уходят в `client.beta.messages.tool_runner`.

Запуск сервера с прокси:

```python
args = ["@playwright/mcp@latest", "--headless"]
if PROXY_URL:
    args += ["--proxy-server", PROXY_URL]
StdioServerParameters(command="npx", args=args)
```

**Обязательно отфильтровать список тулов.** Playwright MCP отдаёт их несколько десятков, все схемы сидят в контексте каждого запроса и размывают внимание модели. Оставляем нужный минимум: навигация, снапшот страницы, клик, скриншот, ожидание.

**Одна сессия браузера на скан, закрывается в `finally`.** Иначе процессы Chromium будут копиться.

**Настройки вызова:** `model="claude-opus-5"`, `max_tokens=32000`, стриминг, `effort="high"`. Длинный агентный заход с десятками вызовов инструментов при тесном лимите обрежется на середине.

**Лимит обхода:** максимум 4 страницы и `max_iterations` в runner'е — чтобы агент не ушёл гулять по всему сайту.

## Границы доверия (в README отдельным разделом)

Это тот пункт, который отличает сданное задание от сданного с пониманием:

- **Модель не имеет доступа к БД.** Она умеет только водить браузер. Все данные о конкурентах читает и пишет `api`, фильтруя по `owner_tg_id` из Telegram-апдейта. Промпт-инъекция со стороннего сайта не может заставить агента прочитать чужие данные — у него физически нет такого инструмента.
- **`owner_tg_id` берётся из апдейта Telegram, не из текста сообщения** и не передаётся модели как аргумент. Модель на него повлиять не может.
- **Вежливый обход:** не больше 4 страниц за скан, пауза между переходами, реальный User-Agent, никакого параллельного долбления.
- Токены в `.env`, `.env` в `.gitignore`. Перед пушем проверить, что ключи не уехали в коммит.

## Порядок сборки

1. **Каркас:** структура папок, `.gitignore`, `.env.example`, `requirements.txt`, venv, `config.py` с чтением прокси. Проверка: venv ставится, `npx @playwright/mcp --help` отвечает.
2. **API + БД без агента:** CRUD конкурентов, схемы, Swagger. Проверка: добавил/получил/удалил через `/docs`.
3. **`scripts/check_mcp.py`:** подключиться к Playwright MCP, вывести список тулов, открыть страницу, снять снапшот и скриншот. Проверка: скрипт печатает содержимое страницы. Это же — материал для демонстрации MCP-сервера.
4. **Фаза 1 — обход:** `tool_runner` с отфильтрованными тулами, промпт обхода, лимит страниц, скриншот главной.
5. **Фаза 2 — извлечение:** `messages.parse` в `Offer`, сохранение снапшота.
6. **Очередь и уведомление:** `POST /scans` → очередь → воркер → `notify.py` шлёт результат в чат.
7. **Бот:** все команды, форматирование сводки, отправка скриншота фото.
8. **Diff и compare.**
9. **Прокси:** когда Гари даст адрес — вписать в `.env`, прогнать `curl` до Telegram, проверить через агента, что браузер видит IP прокси.
10. **README** со схемой архитектуры, разделом про прокси и разделом про границы доверия.
11. **Запись демо** по `docs/demo-script.md`.

Шаги 1–8 не блокируются отсутствием адреса прокси: с пустым `PROXY_URL` всё работает напрямую.

## Проверка

**Поэтапно** (по ходу сборки):
- `.py` → `python -m py_compile <файл>`
- Перед пушем — глазами проверить, что `.env` не в индексе

**End-to-end** (финальная проверка):

Терминал 1: `.\run_api.ps1`  Терминал 2: `.\run_bot.ps1`

1. В боте: `/add https://<конкурент> Название` → «добавлен, id=1»
2. `/list` → видно запись
3. `/scan 1` → «принял в работу»
4. Через 1–3 минуты в чат приходит скриншот + сводка оффера
5. `GET /docs` → `/competitors/1/snapshot` возвращает заполненный JSON по схеме `Offer`
6. `/scan 1` повторно → `/diff 1` показывает изменения (для демо можно подменить одно поле в БД руками, чтобы диф гарантированно был не пустым)
7. В логах `api` видны вызовы Playwright-тулов и их количество

## Сценарий видео (`docs/demo-script.md`)

Требования сдачи — три артефакта, снимаем каждый явно:

1. **MCP-сервер** — `scripts/check_mcp.py`: подключение, список тулов, открытие страницы. Показывает, что сервер отдельная сущность, а не функция внутри бота
2. **API** — Swagger `/docs`, ручной вызов `POST /competitors` и `GET /compare`
3. **Бот** — `/add` → `/scan` → приходит скриншот и сводка
4. **Логи вызовов тулов** рядом с диалогом — видно, что решения о кликах принимала модель, а не `if`
5. **`/diff`** — сравнение двух замеров

Отдельно проговорить голосом или в описании: **почему здесь MCP, а не свои функции** — живой браузер с состоянием между вызовами, модель ориентируется по содержимому страницы, а не по селекторам. Скрипт бы тут потребовал переписывания под каждый новый сайт.
